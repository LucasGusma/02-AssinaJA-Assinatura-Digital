1. Objetivo e limites

O AssinaJA permite acompanhar documentos clínicos fechados que exigem assinatura, consultar responsáveis, transferir documentos elegíveis e consultar o histórico de ações do próprio sistema. A assinatura dos documentos é realizada no MV.

A consulta geral está disponível aos usuários autenticados. A permissão de transferir é individual e global para os setores; somente o usuário master ADMIN pode concedê-la ou retirá-la. Ser master não concede automaticamente a permissão de transferência.

As rotinas de transferência estão na package existente SCHEMA_HOSPITAL.PKG_GERENCIADOR_ASSINATURA. A antiga package de transferência foi removida. A package APP_SCHEMA.PKG_ASSINAJA_ACESSO continua sendo utilizada para perfil, diretório, permissões e consulta da auditoria.

3. Consulta de documentos

A tela chama a API, que utiliza LISTA_PENDENCIAS no Oracle. A tabela principal é PW_DOCUMENTO_CLINICO, relacionada a PAGU_OBJETO, paciente, usuário e prestador.

dc.tp_status = 'FECHADO'
obj.sn_assinatura = 'S'
dc.dh_criacao >= TRUNC(p_dt_ini)
dc.dh_criacao < TRUNC(p_dt_fim) + 1
  • As datas se referem à criação do documento, incluindo integralmente o último dia.
  • O período máximo é de 31 dias; a interface inicia com os últimos sete dias.
  • São apresentados até 50 documentos por página, em ordem decrescente de código do documento.
  • O parâmetro before identifica o limite da próxima página; não se usa deslocamento crescente de registros.
  • Nome do prestador: busca por trecho, ignorando maiúsculas e os acentos previstos na normalização SQL. O filtro é aplicado antes da paginação e aceita até 128 caracteres.
  • No escopo pessoal, o usuário é obtido da sessão do servidor; não é escolhido livremente pelo navegador.
  • O filtro por setor de documentos não está disponível no modo MV atual.

Aparecer na lista não garante elegibilidade para transferência. A função de bloqueio verifica condições adicionais. Apenas consultar documentos não altera registros clínicos.

4. Transferências e auditoria

Fluxo do usuário

  1. Abra Ver detalhes de um documento.
  2. Confira se a transferência está disponível; quando bloqueada, consulte o motivo.
  3. Pesquise e selecione um destinatário ativo com prestador válido.
  4. Informe a justificativa, entre 10 e 1.000 caracteres, e confirme a operação.
  5. Aguarde a confirmação do Oracle; após sucesso, a listagem é recarregada.

Fluxo transacional

A API valida sessão e permissão e envia autor, documento, responsável esperado, destinatário, motivo, chave UUID e identificador da requisição à rotina TRANSFERIR. O Oracle revalida permissões, bloqueia os registros necessários, verifica elegibilidade e sincroniza a origem conforme o tipo documental.

A rotina chama ATUALIZA_PRESTADOR para alterar CD_PRESTADOR e atualiza CD_USUARIO no documento clínico. Assim, a consulta pessoal deixa de selecionar o documento para o usuário anterior e passa a selecioná-lo para o destinatário. A visualização no cliente MV depende também das regras e atualização da própria interface MV.

São preservados paciente, atendimento, estado e datas controladas pela rotina. A transferência não assina, exclui ou fecha um registro aberto no editor. Para anexos, o campo de usuário que identifica quem anexou o arquivo permanece como histórico de autoria do anexo.

A auditoria e o controle de repetição são gravados na mesma transação. O Python confirma com commit somente após receber um identificador válido. Falhas causam reversão; a chave de idempotência evita repetir a mesma transferência em uma nova tentativa com os mesmos dados.

Cobertura registrada

O código consolidado contém regras para: PRESCR, ENFERM, TRATMT, AFERIC, ALTMED, AVALIA, DIAEST, DIAENF, HISENF, RESENF, DOCELE, ANEXO, ANOENF, EVOMED e MEDICA. A documentação anterior registra testes com rollback desses 15 tipos; esses testes não foram repetidos nesta atividade.

EXAFIS e GRUDOC permanecem fora da cobertura homologada documentada. Documentos assinados, vínculos inconsistentes e certas urgências com prestador geral são bloqueados. A rotina restringe a execução à base smlmv; a documentação não constitui autorização de implantação em produção.

7. API

Prefixo funcional: /api/v1. Rotas de negócio exigem sessão, salvo login e status. Alterações exigem origem permitida, JSON e o cabeçalho X-CSRF-Protection: 1.

Método e rotaUso
POST /auth/login · GET /auth/session · POST /auth/logoutAcesso, consulta de sessão e saída.
GET /statusConfiguração e capacidades; não testa o banco por si só.
GET /documentsstart, end, scope=all|mine, provider opcional e before opcional.
GET /documents/{id}/recipientsBusca de destinatários; parâmetro search.
POST /documents/{id}/transfersrecipient, reason, idempotency_key e expected_owner.
GET /sectors · GET /users?sector={id}Diretório de setores e usuários.

Fora desse prefixo: /api/health/live verifica o servidor; /api/health/ready consulta o Oracle e verifica objetos/rotinas necessários. O esquema OpenAPI fica em /api/openapi.json fora de produção; as interfaces Swagger/ReDoc estão desativadas.

8. Segurança e desempenho

  • Cookie de sessão HttpOnly e SameSite Strict; Secure obrigatório na configuração de produção.
  • Tokens aleatórios, armazenados como hash em memória no backend; duração padrão de uma hora, configurável.
  • Um único worker no modo MV atual: reiniciar o processo encerra as sessões; múltiplos workers não compartilham o armazenamento.
  • Limite local de 20 tentativas de login por endereço em cinco minutos.
  • Validação de Host e Origin, cabeçalhos de segurança e limite de 8 KiB para corpos de requisições de alteração.
  • Parâmetros SQL vinculados; validação de tipos, limites, paginação e respostas do Oracle.
  • Pool Thick por processo: padrões de mínimo 1, máximo 5, espera de aquisição 3 segundos e timeout de chamada 15 segundos.
  • Consultas em transação somente leitura no adaptador; operações de escrita controladas e rollback na devolução da conexão.
  • Erros ao cliente não expõem senha ou SQL bruto; request_id permite correlacionar diagnósticos.

9. Configuração e execução

Pré-requisitos: Python e ambiente virtual compatíveis com as dependências fixadas, Node/npm para compilar o frontend, Oracle Instant Client compatível com a arquitetura do Python e acesso de rede ao serviço Oracle. As versões efetivas devem ser conferidas no ambiente de implantação.

O .env é lido na raiz do projeto; variáveis do processo têm precedência. Para iniciar no PowerShell, já na pasta AssinaJA:

.\.venv\Scripts\python.exe server.py

Acesse http://127.0.0.1:8765. Não é necessário ativar o ambiente virtual ao usar o executável completo. Mantenha o terminal aberto; Ctrl+C encerra o processo.

Instalação de dependências e compilação, quando necessárias:

.\.venv\Scripts\python.exe -m pip install -r backend/requirements.lock.txt
npm.cmd --prefix frontend ci
npm.cmd --prefix frontend run build

Para desenvolver o React, mantenha o backend em execução e use outro terminal:

npm.cmd --prefix frontend run dev

Use o endereço exibido pelo Vite. O servidor de desenvolvimento encaminha /api para o backend local. Alterações em .env ou Python exigem reinício no comando padrão; alterações no frontend servido pelo backend exigem novo build.

Os arquivos SQL locais são snapshots para revisão, não prova de que o banco continuará idêntico após mudanças externas. Documentos antigos do projeto podem descrever etapas anteriores; esta versão documenta a consolidação atual, sem executar migrações.
